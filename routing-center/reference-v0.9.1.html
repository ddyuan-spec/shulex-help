“队列路由”是新的分单执行方式；Trigger 是与它协作的独立业务规则。 分单中心统一管理，规则表达要求，队列确定团队，技能与接单资格筛选候选，统一提交负责人并解释结果。

2.1先统一名称和职责

建议客户在同一已纳入渠道上，选择“现有分单方式（兼容）”或“队列路由”之一。 Trigger 是始终独立的通用业务规则能力，不是新模式的开关，也不是 Routing 的子功能。队列路由没有任何 Trigger 分单规则也能工作：直接按队列条件匹配和兜底队列分配；需要 VIP、特定事件等例外时再组合 Trigger。

启用“队列路由”成功后，系统自动阻止适用渠道的旧自动分单动作执行，保留配置并显示“由队列路由接管”。客户无需逐条手动停用，也不能在后台绕过模式开关重新启用旧分单。旧规则中的合并/关单、通知等非分单能力不因此失效。

“待废弃”只指旧自动分单执行方式的产品演进方向，不代表本次立即删除或已有退役日期。现有实现本身允许 Queue 与旧规则接管/回退，因此当前行为还不是严格二选一；新方案必须增加统一的执行边界。已迁移渠道不会在队列未命中、无人可用或技术失败时重新调用旧分单。

2.2功能关系：管理入口与运行过程分开看

客户唯一分单入口：设置 → 分单中心。 同一页按“分单规则（关联 Trigger）→ 承接队列 → 试单与发布”组织功能，保持与运行顺序一致。分单规则决定进入哪个队列；队列决定承接团队、选人和等待。两者属于同一入口。Trigger 保持独立通用业务能力；分单中心以同一规则 ID 展示和编辑其分配动作，不复制规则。新模式下从独立 Trigger 选择分配动作时，进入分单中心的关联编辑器并可返回来源；不再暴露一条可绕过路由的直接写入路径。旧自动分单入口在迁移范围只显示只读迁移提示与分单中心链接。

分单规则展示完整分类位置、规则次序和关联通用动作。调序同步到原 Trigger，含标签准备/通知等混合动作时先展示影响，不能在分单中心暗建独立排序。通用 Trigger 按既有事件/多轮机制准备字段；分单读取同一事件稳定事实后计算意图，归属仅提交一次。存在事实依赖环或读取临时负责人副作用的旧规则，属于迁移阻塞项；技术设计须落地稳定事实与执行终止边界。

分单方式是管理员提前选择的执行边界，不是每张工单都重新迁移一次。运行时优先保护已有负责人；Trigger 可选参与，队列也能独立分单。

  • 普通分类交给队列。 已有字段能直接表达“哪类工单交给哪个团队”时，在队列配置条件即可。
  • 业务例外交给 Trigger。 需要事件、标签准备、目标队列或优先客服时，复用独立 Trigger；通用动作不因分单模式切换而停用。
  • 技能决定能不能处理（二期）。 队列决定团队范围；技能要求与客服技能求交，不替代团队或权限。必需技能不超时降级，可选技能可按政策放宽。
  • 接不接得了由接单条件决定。 在线、营业时间和容量统一检查，不让每条 Trigger 重复承担选人逻辑。
  • 旧自动分单与队列路由二选一。 成功切换后，迁移范围内的旧分单自动不执行；不因新模式满载或失败而回退旧分单。

2.3三种顺序与两类分配动作

  • 规则生效顺序： 哪条分配要求被采纳。首个有效分配动作胜出。
  • 队列匹配顺序： 工单归入哪个队列。首个匹配胜出，不等于此队列永远抢先处理。
  • 待分配顺序： 哪张等待工单先尝试接单。首期同渠道、同一个候选坐席可服务的等待项按首次进入当前周期的时间 FIFO；跨队列也沿用此顺序，时间相同按稳定 ID。跨 Chat/Email 不新增共同抢占优先级，按各自容量分配。

选人继续使用已核实的队列策略：剩余容量优先、同余量按最久未分配、再按稳定 ID。首期不向客户承诺绝对平均或严格轮询；后续引入策略选择需独立验收。

分配动作 必填 结果
转入队列 目标队列 由队列团队统一选人或等待
优先指派客服 目标队列、该团队内客服 客服符合条件则分给他；暂时不可接单则由该队列团队承接

“按排班指派”合并为优先指派的可选生效日历，而不是第三种独立分单方式。该日历表示该例外规则何时生效；非排班时跳过该动作并继续找后续分单规则，最后仍可走普通队列。团队营业日历表示这个团队何时接单，两者用途不同。界面直接展示这两句说明。

同一条规则首期最多一个分配动作，避免“指定 A 后又转队列 B”。引用失效（队列删除、客服移出团队、日历无效）是配置错误：阻止保存；运行时若出现则记录失败并进入主管待处理，不静默降级。与“客服当前离线/满载”这种正常不可用情况分开。

旧 ASSIGN_MEMBER 的强制直接指派不自动改名成“优先指派”。迁移检查必须列出其覆盖、离线、排班行为差异；不能等价转换的保留旧模式直至管理员选择目标行为。

2.6Zendesk 借鉴与差异展开细则

查阅日期：2026-11-03；以下来自官方产品文档，不是 Zendesk 账号实测。

Zendesk 的 Trigger 不属于 Routing。 官方导航明确区分：

  • Admin Center → Objects and rules → Business rules → Triggers：通用条件/动作规则，用于字段更新、分配、通知等。
  • Admin Center → Objects and rules → Omnichannel routing → Queues：队列与路由配置。

它们的关系是通用业务规则与路由能力协作。不能因为 Trigger 在路由之前执行，就把整个 Trigger 放进 Routing。Tars 也应保持同级独立入口；“关联分单的 Trigger”只是筛选视图。

3.3二期技能：目录、要求、匹配与变更展开细则

技能不是团队的别名。 团队描述组织归属，技能描述客服的处理能力。同一客服可具备多个技能，同一技能可被多个团队使用。用例：退款队列归售后团队，工单要求德语，退款经验为可选；仅在售后团队内先找“德语 + 退款”客服，放宽后仍必须会德语。

配置对象与入口

对象 配置位置与权限 字段与规则
技能目录 设置 → 技能；有路由配置权限的管理员 稳定 ID、唯一名称、分类（语言/产品/业务）、启用状态；改名不影响引用，停用前显示依赖并阻断活跃引用，不物理删除历史

来源合并规则： 采用所选队列默认要求与本轮所有适用 Trigger“添加技能要求”动作的并集。重复技能去重，同一技能一处必需、一处可选时，必需优先。首个有效分配动作只决定目标队列/优先客服，不截断其他规则的字段、通知或技能追加。二期不开放自动规则删除/覆盖技能要求，避免后执行规则降低要求；需要修改当前周期要求时由有权限管理员显式重评估。

不同必需技能之间为 AND，多个可选技能在放宽前也须全部满足。不默认支持“德语或法语”、技能等级或按数量打分；如误配“德语且法语”，界面展示交集候选数，不擅自改成 OR。未知或停用技能引用属于配置错误；当前没有具备技能的人属于资源不足，两者分别展示。

候选选择与计时

  1. 已有负责人保护仍在最前面。新技能或人员技能变化不自动抢走正在服务的工单。
  2. 确定队列及候选团队，一期/二期为单团队；三期扩展主/备用团队。
  3. 过滤有效成员、权限、营业/排班、在线连接和渠道容量，然后检查全部必需技能与尚未放宽的可选技能。管理员看到各原因排除人数与最终交集。
  4. 二期沿用“当前客服可服务工单中的 FIFO”：技能不匹配的队首工单继续等待，不能堵住该客服能够处理的后续工单。四期再扩展优先级/SLA，不把避免技能阻塞推迟到四期。优先客服也必须通过上述条件。优先客服技能不符或不可用时，按既有剩余容量/最近分配顺序选择同范围其他合格客服。
  5. 无合格客服时，依据渠道准入政策进入等待或退出。Message 全队离线/营业外维持已定义的渠道处理；有可接资源但技能不符时进入技能等待，仍受总排队上限约束。
  6. 可选技能计时从本轮入队开始，按自然时间持续计算。 不是建单时间，不从排到队头才计时，不因轮询、标签变化、进程重启、跨团队溢出或编辑规则而重置。二期采用一个统一时限、到期一次性放宽全部可选技能；关闭放宽则持续保留技能要求直至渠道总等待期限。配置值必须为正整数秒且小于有限的总排队上限，示例值不作为默认 SLA 承诺。
  7. 放宽只改变可选技能筛选；必需技能、权限、在线、营业与容量永不放宽。若仍无人可接，继续等待并说明原因，不自动转旧规则或下一队列。
  8. 同时到达总排队截止与技能截止时，先按总排队退出/主管处理政策结束本轮尝试，不能用技能放宽重新开启已到期周期。技术失败或未知结果也不能被伪装成技能超时。

与 Zendesk 的取舍： 借鉴必需/可选技能及超时放宽，但不照搬其各渠道技能时钟。Zendesk Email 技能超时与到达队首后的等待相关，Messaging/Call 与匹配客服持续不可用相关；Tars 二期建议统一从入队起算，以便解释、复现和跨实例恢复。此差异必须在产品帮助及迁移说明中明示。官方依据：Z4。

更新、人工操作与边界

  • 工单技能要求、放宽时限与队列政策按当前周期冻结；普通字段变化只影响后续周期，当前周期显式重评估后记录新版本，不重置本轮累计等待和总截止。新增可选技能若其时限已过，立即显示为已放宽；不得借重评估延长总等待。
  • 客服技能资格实时读取：撤销技能影响尚未提交的分配；提交前再次校验资格版本。已提交的在办工单保持原负责人，向主管提示能力变化，由主管处理；不静默重分。
  • 手工转派和优先指派同样不能突破必需技能、权限和硬容量。可选技能已放宽则正常选择，未放宽时可通过“交回并显式重评估”改变要求，需说明差异并留审计。首期明确允许的 Email 离线手工指派仍单独提示。
  • 技能的设置不代表完成 AI 转人工；HITL 审核是否适用技能先做任务/服务周期映射。
  • 管理员发布前至少看到“团队内具备全部必需技能的人数”。为 0 时阻断新配置启用；正常成员变动后变成 0，则阻断新分配并可见告警，不删除技能要求。
  • 二期回退不能直接关技能过滤。未启用技能的队列可继续一期行为；有技能要求的活动周期保留技能执行器或暂停待人工处理。只有零依赖、零活动技能周期时，才能完全回退二期服务。

现有 Queue Routing 开关仍然是旧产品能力，不等于新统一分单模式。新机制需要清晰的版本/模式标识。

  • 旧模式：原自动规则、Trigger 与 Queue 行为保留，统一入口展示实际关系和冲突提示。
  • 统一模式：已纳入渠道的所有自动分配入口都走统一提交；不允许旧指派动作在后台继续直接写负责人。未纳入渠道明确保留旧模式。
  • 首期按租户及已支持渠道整体切换，不做同渠道随机抽样双写。事件和服务周期绑定所用模式/版本。
  • 旧活动周期按原版本完成；新模式从新周期启用。切换必须先阻断新的旧模式请求，并检查在途旧写入，不仅关一个 UI 开关。

  • 结果未知：不显示“发布成功”或“分配失败”；先查询版本/决策状态，再允许安全重试。

队列已选中不等于分配成功。 一张工单沿同一服务周期判断资格、选择客服、提交归属；无资源时等待，配置或技术异常单独恢复，人工接手后受保护。

4.1从进入人工服务到完成分配

  1. 检查资格和当前归属。 只处理需要人工、允许分配且未被保护的工单。AI 正在处理且未转人工/未进入允许人工介入的状态、已结束服务均不分单。
  2. 准备业务事实。 完成本轮相关本地字段/标签规则，得到稳定事实；外部 Webhook、通知和异步 AI 结果不阻塞这一阶段。之后收到新事实，按新的工单版本处理。
  3. 计算分配要求。 复用 Trigger 的分类/规则排序；在“分单规则”视图可看到完整相对顺序。同一轮首个条件及动作前置条件成立的分配动作生效。该轮其他分配动作标记“已有更高顺序规则生效”；非分配动作继续按既有规则语义运行。
  4. 确定队列。 有显式队列目标则使用它；否则按队列顺序首个匹配；仍无匹配进入本渠道显式兜底队列。显式队列选择跳过该队列的普通匹配条件，但不能绕过渠道、租户、团队、日历及资格校验。
  5. 尝试选人。 有优先客服时先检查该客服；不满足在线/容量等接单条件时回到同一个队列的团队选人，不阻塞后续工作，也不转给另一条低优先规则。
  6. 记录结果并等待或结束。 原子提交负责人、当前服务状态和容量；无空位按渠道政策等待，资源变化后重试。技术失败进入可恢复失败，不因异常退回另一套规则。

二期在步骤 2–4 汇总技能要求，在步骤 5 选人前统一过滤技能；三期在同一队列内扩展团队范围并增加可选接单确认；四期调整等待工单的调度顺序。不会为每一期再建立独立执行链。

这是目标语义，当前 Trigger 与队列尚未具备这条完整顺序。第一条路由动作优先与现有 Trigger 多规则直接写入的语义不同，必须经迁移确认；不能把两者混用后称为统一机制。

图中“跳过自动分配”只跳过分配路径，不会整体停止 Trigger 的标签、通知等通用动作。显式目标队列或日历引用失效属于配置异常，不等于“没有规则命中”；必须修复，不能静默走普通匹配。选择队列不等于已经分配成功，只有实际写入负责人后才显示“已分配”。

队列已经等待时，资源变化重试当前队列，不重新运行全部分单规则。普通字段变更首期不静默换队列，主管可显式重新评估。图中的排队超时是 Tars 建议政策，不是 Zendesk 的统一机制；一期、二期不引入“客服收到邀请后超时未接”的独立接单邀请状态机；三期按 Message 渠道协议增加。后者与排队等待、可选技能等待不同。

4.2从工单入口验证归属与恢复

分单记录 → 过滤“等待” → 打开工单 → 看到“售后队列，在线 2 人，均无剩余容量” → 选择合格客服接管或调整团队资源 → 看到分配成功 → 刷新后仍为同一归属。查看团队成员数据需具备相应权限。

“未命中”“等待”“跳过”“失败”必须分开：未命中是条件不符；等待是已选定团队暂无接单条件；跳过是保护/排班等正常结果；失败是配置或系统未完成。

第 4 章采用可播放、暂停、前后单步和重播的工单流转动画。工单卡沿“进入 → 归属保护 → 规则 → 队列 → 技能 → 候选 → 等待 → 结果”移动；每一站展示当时的输入、判断与去向。动画始终预演新机制草稿，与当前演示发布模式明确区分。

等待中 主管选择另一队列 更新队列与版本，保留本轮最初等待时间，取消旧等待资格

队列与规则配置版本对新周期生效；已有等待工单保留原队列/政策快照，失效引用转配置异常。成员停用、离组、连接、容量等实时资格始终重查；不能因为冻结了政策而把工单分给失效成员。

AI 处理、人工审核、正式转人工是不同服务状态。分单规则只在状态允许人工承担工作时运行；设置负责人本身不等于已完成转人工。HITL 审核任务是否占用与实时人工会话相同容量，现有模型需复核后决定；未明确前不把所有 AI 工单投入人工队列。

4.6三期、四期怎样扩展同一条链展开细则

三期：扩大团队范围与恢复未接单工作。 队列配置一个主团队池和备用团队池；本轮入队后达到溢出阈值，候选池从主团队扩为主 + 备用，去重客服并继续校验全部必需技能、尚未放宽的可选技能与容量。主团队恢复后不把已接受的工作抢回。不是按队列列表“转到下一队列”，也不覆盖原队列、技能和等待时钟。与技能放宽阈值可以不同；每次唤醒按当前时间一次性计算适用范围，若总排队已到期则先结束。

Message 接单邀请作为可选策略：创建有到期时间的容量预留和邀请 ID，接受时原子确认归属；拒绝/超时则释放该邀请预留并重投其他合格客服，记录本轮尝试过的客服、尝试次数上限和无候选冷却。迟到接受、旧邀请回放不得生效。总排队上限覆盖所有邀请尝试；到期与接受竞争只有一个有效终态。Email 默认直接分配，不伪造接单邀请；Voice 后续单独适配既有通话/Reservation 状态机。

受控自动转派只对管理员启用的“未接受邀请”或其他明确许可状态生效。在办工单下线后转派仍需单独策略、人工提示与审计；不能因为存在 SLA 或超时就默认抢单。三期上线门槛包含渠道是否支持可撤销邀请、幂等接受和客户侧状态同步。

四期：决定可服务工单中谁先分。 队列匹配顺序仍只决定归属，不兼任调度权重。调度在同租户、同路由渠道、同一候选客服能处理的等待工单间选择；管理员可选“优先级 + 等待时间”或“SLA 最早到期 + 等待时间”，同值按稳定 ID。SLA 模式下已违约工单也保留并优先处理，不自动关闭；无 SLA 的工单按普通等待规则处理。增加老化保护及无 SLA 保障份额，具体阈值在基线后评审，不能承诺无条件 SLA 达标。

必须跳过当前客服不具备技能/权限的工单，避免一张无人能处理的队首工单堵住其他工作。配置变更对新周期生效；若要调整在队排序，应显式展示影响范围。运营看板拆分无容量、无必需技能、等待可选技能、待溢出、未接受邀请、技术失败和已违约，而非只显示“排队中”。

5.5工程约束与发布后观察展开细则

本轮用户走查补充原则： 可用性验收必须让没有参与设计的人，根据界面独立回答“在哪配、谁先判断、什么被跳过、为什么分给此人、无人可接怎么办”。页面能加载、动画能播放、每个按钮有响应都不能代替理解验收。配置→试单必须共享真实演示状态；每一步展示输入、判断证据与结果，禁止用互不连续的独立样例伪装完整流程。

复用 Trigger 条件能力、Queue/Team/Calendar/Capacity、HSR 与持久命令/Outbox。新增或扩展决策记录保存来源、工单版本、配置版本、周期和原因；具体表结构在技术设计时决定。

关键前置是完整盘点所有负责人写入方：Trigger、旧 Automation、Queue、人工/批量、OpenAPI、渠道建单/重开/转人工。必须统一提交校验，不能只改三个入口；首期之外的写入方必须有清晰兼容适配或不进入新模式。

规则阶段要区分本地业务事实准备与分配意图求值；复用现有定义、做目标模式的执行阶段拆分，不能靠 sleep 等待两个异步消费者“碰巧顺序正确”。外部副作用走独立幂等执行；分配失败不能重放整条规则造成重复通知。

以租户 + 工单 + 服务周期为归属并发单位，以租户 + 坐席 + 渠道为容量单位。提交同时复核版本、资格和容量；冲突重新评估，不静默最后写入覆盖。分布式锁竞争失败保留待处理并重试，不当作已完成；锁粒度、续租/超时、进程崩溃后恢复需在技术详设中明确。持久状态、条件更新和幂等键必须共同兜底，不能只靠 JVM 或 Redis 锁。

队列唤醒与补偿扫描需要多实例 claim/去重；本轮跳过的记录保留可扫描状态。DB 主事实与 ES/通知分别核对；技术失败、结果未知、业务不可接单不能共用一个“失败”状态。
